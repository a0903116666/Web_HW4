## 背景

目前的專案只是預設的 Express 骨架，只有靜態首頁，還沒有資料庫層。這份作業需要一個本機網站，可以接收價格資料、在重新整理後保留資料，並以簡單可查詢的方式顯示價格歷史。整體實作要維持輕量，不能引入前端框架。

## 目標 / 非目標

**目標：**
- 建立一個以維力炸醬麵為主題的單一商品價格追蹤網站。
- 讓介面足夠簡單，能快速提交日期、商品名稱與商品價格。
- 將資料儲存在 SQLite 中，重新整理後仍可讀回。
- 以表格或清單顯示歷史資料，並支援基本篩選。
- 讓安裝與展示步驟容易整理成教學文件。

**非目標：**
- 抓取外部網站的即時價格資料。
- 使用者帳號、驗證或多人協作。
- 雲端部署或正式上線強化。
- 超出作業需求的分析、圖表或進階報表。

## 設計決策

- 使用靜態的 HTML / CSS / JavaScript 前端，而不是伺服器端模板。
  - 理由：作業明確允許純前端，靜態頁也更容易說明流程。
  - 其他方案：使用 Express 模板頁，或導入前端框架。兩者都會增加複雜度，但不會明顯提升作業成果。

- 提供一組小型 REST 風格 API，負責新增、列出與篩選資料。
  - 理由：前端可以直接用 fetch 呼叫，API 也容易測試。
  - 其他方案：傳統表單提交搭配整頁刷新，或 GraphQL。對這個範圍都沒有必要。

- 使用 SQLite 作為本機持久化層，並以一張表存放價格資料。
  - 理由：SQLite 很適合單機單人流程，不需要額外服務就能看見持久化效果。
  - 其他方案：JSON 檔案儲存雖然更簡單，但不符合資料庫要求；MySQL / PostgreSQL 則太重。

- 預先建立三筆示範資料，讓第一次執行就能展示價格變化。
  - 理由：作業要求至少三筆測試資料，預先建立可提高展示的穩定性與可重現性。
  - 其他方案：每次都手動輸入，對截圖與教學內容較不可靠。

- 主要查詢互動採用文字關鍵字篩選顯示中的歷史資料。
  - 理由：這樣就能滿足「簡易查詢」的需求，不必強迫做複雜搜尋介面。
  - 其他方案：日期區間選擇器或多重條件篩選，工作量會更高。

## 風險 / 取捨

- SQLite 檔案損毀或誤刪 -> 將資料庫放在獨立資料夾，並在文件中說明如何重置。
- 種子資料在重複啟動時可能重複插入 -> 只在資料表為空時才初始化資料。
- 專案可能超出作業範圍 -> 第一版就保持聚焦在一個商品、一張表與一條查詢流程。
- 教學文件是 app 以外的交付物 -> 將 HackMD / Notion 文件視為搭配成果，而不是執行時程式的一部分。

## 遷移計畫

- 若資料庫檔案不存在，第一次啟動時建立它。
- 只有在資料表為空時才建立示範資料。
- 若日後 schema 改變，可在開發階段加入小型升級步驟，或直接重建本機資料庫。
- 回復方式很單純：還原前一版資料庫檔案，或刪除生成的本機資料庫後重新啟動。
